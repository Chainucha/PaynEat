# PaynEat POS — Feature Gap Analysis (มุมมอง PO)

วันที่วิเคราะห์: 2026-09-09 (re-verify ล่าสุด 2026-09-19 — ดู `docs/DECISIONS.md` #35)
ผู้วิเคราะห์: PO review (ผ่าน Claude Code) โดยอ่านโค้ดจริง + README + `docs/DECISIONS.md`

เอกสารนี้สรุปว่าฟีเจอร์ POS พื้นฐานอะไร **มีอยู่แล้ว** และอะไร **ยังขาด** เทียบกับสิ่งที่ POS
ร้านอาหารทั่วไปต้องมีเพื่อใช้งานจริง (ไม่ใช่แค่ demo/portfolio) ใช้เป็น input สำหรับตัด ticket
พัฒนาต่อ — ดู tickets ที่เกี่ยวข้องใน `docs/tickets/` (สร้างจากเอกสารนี้)

## สรุปสำหรับ PO (2026-09-19): พร้อมให้คนโหลดไปใช้จริงหรือยัง แม้จะฟรี?

**พร้อมแล้วสำหรับร้านอาหารเดี่ยว (ไม่ใช่เชนหลายสาขา)** — 🔴 Critical และ 🟠 High ทุกข้อ (ticket
1-8, 16) ผ่านการตรวจโค้ดจริงซ้ำอย่างน้อย 2 รอบแล้วว่าทำจริงครบ (DB + backend + UI ที่ผู้ใช้กดได้จริง)
ไม่ใช่แค่ป้ายชื่อ — ล่าสุดสุ่มตรวจ shift/refund/inventory/tax-invoice อิสระอีกรอบ (2026-09-19) ยืนยัน
PASS ทั้งหมด ไม่พบร่องรอยของปลอม/cosmetic แบบที่เคยเจอใน ticket 16 (PromptPay QR) ตอนแรก บวกกับ
ticket 15 (AI ถามตอบข้อมูลร้านด้วย LLM) ที่เป็นจุดขายที่คู่แข่งฟรี/เสียเงินส่วนใหญ่ในตลาดไทยยังไม่มี —
ครบทั้งเรื่องพื้นฐานที่ POS ทุกตัวต้องมีและเรื่องที่ทำให้ "ฟรีแต่ไม่ด้อยกว่าของเสียเงิน"

**อัปเดต (ยังวันเดียวกัน 2026-09-19):** ตอนแรกระบุว่า gap #12 (export รายงาน/Z-report) เป็นสิ่งเดียว
ที่ยังเป็นแรงเสียดทานจริง แล้วเขียน full spec ให้ทันที — **หลังจากนั้นพบว่ามีอีก session ทำ #12 จริง
เสร็จไปแล้วขนานกัน** บน branch `claude/pos-restaurant-project-3djpp6` (ยังไม่ merge เข้า main) และ
พบเพิ่มว่า **#11 multi-branch ก็กำลังถูกทำอยู่ขนานกันเช่นกัน** (backend เสร็จ ยังไม่มี UI) ทั้งที่
เพิ่งยืนยันไปว่า "ยัง out-of-scope ไม่มี drift" — บทเรียน: การ "ตรวจโค้ดจริง" ที่ทำมาตลอดเซสชันนี้
ตรวจได้แค่โค้ดที่มองเห็น ณ ตอนนั้น (`main` + branch ของเซสชันนี้เอง) ไม่ครอบคลุม branch อื่นที่
session อื่นกำลังทำขนานกันอยู่ในโปรเจกต์แบบ multi-session นี้ — ดูรายละเอียดที่
`docs/tickets/12-report-export.md`, `docs/tickets/11-multi-branch.md`

**สรุปที่ยังยืนอยู่**: 🔴 Critical + 🟠 High เดิม (ticket 1-8, 16) ครบและ verified จริง, ticket 15
(AI) เป็นจุดขาย — เพียงพอสำหรับร้านเดี่ยวให้คนโหลดไปใช้จริงได้ ไม่มี gap ที่ยังค้างจริงในกลุ่มนี้แล้ว
(12 เสร็จ, 11 กำลังทำ ทั้งคู่รอ merge เข้า main)

**อัปเดต 2026-09-23 (มีผู้สนใจจะเอาไปใช้ในร้านจริง):** ก่อนส่งให้ร้านจริงใช้ เขียนชุด E2E ที่ให้แอปตัวจริง
คุยกับ backend ตัวจริงผ่าน HTTP (`app/test_e2e/` 30 เคส) — รอบแรกเจอ**บั๊กจริง 5 ตัว**ที่ทั้งการตรวจโค้ดซ้ำ
2 รอบข้างบนและเทสต์เดิม 659 ตัวไม่เจอ แก้ครบแล้ว (ดูหมายเหตุ #43–#47 ด้านล่าง) — บทเรียนต่อจากย่อหน้า
ก่อน: "ตรวจโค้ดจริงว่าทำครบ" ยืนยันได้แค่ว่าแต่ละฝั่งมีของ ไม่ได้ยืนยันว่า**สองฝั่งตีความตรงกัน** — เทสต์
Flutter ทั้งหมดวิ่งบนโหมดสาธิตซึ่งเป็นตรรกะอีกชุดที่เขียนเลียนแบบ backend ส่วนเทสต์ backend ไม่เคยให้
โค้ด Dart อ่าน JSON จริง ช่องระหว่างสองฝั่งนี้จึงไม่เคยถูกเทสต์เลยจนถึงวันนี้

**อัปเดต 2026-09-23 (ผู้สนใจรายแรกเป็นร้านเนื้อ + ผู้กระจายสินค้า):** ผู้ที่จะเอาไปใช้จริงรายแรก (MEET365)
ไม่ใช่ร้านอาหารล้วน — มีเคาน์เตอร์ขายเนื้อสดเป็นกิโลและส่งเนื้อให้ร้านอาหารอื่นแบบเครดิต ตรวจแล้วเจอ gap
ใหม่ 3 ข้อที่ไม่อยู่ในรายการเดิมเพราะรายการเดิมคิดจากมุมร้านอาหารอย่างเดียว: ขายตามน้ำหนักไม่ได้, ไม่มี
บาร์โค้ด/ฉลากตาชั่ง, ไม่มีขายเชื่อ/วางบิล — **ทำครบทั้งสามข้อแล้ว** (ticket 18–20, ดูหมายเหตุ #48–#51
ด้านล่าง) พร้อมชุด E2E ใหม่ที่เดินเคาน์เตอร์เนื้อ → ขายเชื่อ → วางบิล → รับชำระ → ปิดกะเงินตรง
รอบต่อมาผู้ใช้ขอให้ทำ 3 ข้อที่เคยตั้งใจไม่ทำต่อด้วย — ตาชั่งต่อสาย + สแกนด้วยกล้อง, ดอกเบี้ยผิดนัด +
ใบลดหนี้, ใบวางบิลเป็น PDF ส่งอีเมล — **ทำครบแล้ว** (ticket 21–23, ดูหมายเหตุ #54–#57 ด้านล่าง)

ระหว่างตรวจซ้ำรอบนี้ยังพบบั๊กจริง 1 จุดใน ticket 15 (AI assistant เคยหลุดตอบข้อความดิบที่ไม่ผ่าน
`submit_answer` ได้ในบางเงื่อนไข ขัดกับสัญญา "ห้ามเดา/แต่งคำตอบ" ของฟีเจอร์เอง) — **แก้แล้วในรอบนี้**
พร้อมเทสต์คุม ไม่ใช่แค่บันทึกทิ้งไว้ ดู `docs/DECISIONS.md` #35

## สิ่งที่มีอยู่แล้ว (ยืนยันจากโค้ดจริง)

- ผังโต๊ะ + สถานะ (available/occupied/reserved/billing), ย้ายโต๊ะ, รวมบิล (merge)
- สั่งอาหาร + modifier/option group, บันทึกครัว, ตะกร้ารวมรายการซ้ำอัตโนมัติ
- ลูกค้าสแกน QR ที่โต๊ะสั่งอาหารเองได้โดยไม่ต้อง login ดู `docs/tickets/17-qr-self-order.md`
- ครัว (KDS) realtime ผ่าน Socket.IO, แจ้งเตือนออเดอร์ค้างนาน
- ชำระเงิน 4 ช่องทาง (cash/qr/card/transfer — `qr` แสดง QR พร้อมเพย์จริงให้ลูกค้าสแกน ดู
  `docs/tickets/16-promptpay-qr.md`), แบ่งจ่ายหลายช่องทาง, แบ่งบิลตามรายการ/ต่อคน
- ส่วนลดแบบ manual ต่อบิล (%, บาท) และโปรโมชันแบบตั้งเงื่อนไขล่วงหน้า (percent/amount/bogo,
  เงื่อนไขวัน/เวลา/เมนู-หมวดหมู่/ยอดขั้นต่ำ, auto-apply หรือรับโค้ดส่วนลด)
- ใบเสร็จบนหน้าจอ + พิมพ์จริงผ่านเครื่องพิมพ์ความร้อน ESC/POS บนวง LAN/WiFi
- เปิด/ปิดกะ + กระทบยอดเงินสด, คืนเงินหลังชำระเงินแล้ว (เต็มจำนวน/บางส่วน)
- Offline mode สำหรับสั่งอาหารเพิ่มเข้าออเดอร์เดิม (queue ในเครื่อง + sync อัตโนมัติ)
- Dashboard + รายงานย้อนหลัง (ยอดขายรายวัน, สินค้าขายดี, สัดส่วนการชำระเงิน)
- จัดการเมนู/หมวดหมู่, จัดการพนักงาน + RBAC 5 role (admin/manager/waiter/cashier/kitchen)
- ตั้งค่าร้าน (VAT rate, service charge, VAT-inclusive toggle)
- คำนวณ VAT + service charge ตรงกันทั้ง frontend/backend มี test คุม
- สต๊อก/วัตถุดิบตัดอัตโนมัติตอนขาย + ใบกำกับภาษี (ย่อ/เต็มรูป) + audit log ครบทั้งระดับผู้จัดการร้าน
  และบัญชี/การเงิน + ลูกค้า/แต้มสะสม + takeaway/delivery flow ในระบบ
- **ผู้ช่วย AI ถามตอบข้อมูลร้านด้วยภาษาพูด** (admin/manager) ผ่าน Claude API + tool-calling ที่เรียก
  endpoint จริงในระบบเท่านั้น กันตอบมั่ว/แต่งตัวเลข ดู `docs/tickets/15-ai-ask-your-data.md`
- **ขายตามน้ำหนัก** (ราคาต่อกิโลกรัม เก็บน้ำหนักเป็นกรัม) + **สแกนบาร์โค้ด/ฉลากตาชั่ง EAN-13** +
  **ขายเชื่อ/ใบวางบิล/รับชำระหนี้** สำหรับลูกค้าขายส่ง ดู `docs/tickets/18-sell-by-weight.md`,
  `19-barcode-scale.md`, `20-b2b-credit.md`
- **สามภาษาทั้งระบบ: ไทย / English / 한국어** สลับได้จากหน้าตั้งค่าหรือหน้าโปรไฟล์ จำค่าไว้กับเครื่อง
  ฝังฟอนต์เกาหลีแบบ subset มาในแอป (ไม่พึ่งฟอนต์ของเครื่อง) และผู้ช่วย AI ตอบภาษาเดียวกับคำถาม
  ได้ทั้งสามภาษา — ดู `docs/DECISIONS.md` #39

## Gap ที่พบ (เรียงตามความสำคัญ)

### 🔴 Critical — บล็อกการใช้งานจริง (ร้านจริงต้องมี ไม่ใช่ของเสริม)

✅ **ทั้ง 5 รายการทำครบแล้ว** (ดูรายละเอียดที่ `docs/tickets/01-04-*.md` และ
`docs/DECISIONS.md` #11/#13 สำหรับขอบเขตที่ตั้งใจจำกัดไว้) — ระหว่างตรวจโค้ดจริงซ้ำอีกรอบ
(2026-09-15) เคยพบ gap ใหม่ที่ไม่เคยอยู่ในรายการนี้มาก่อนคือ **#16 PromptPay QR ยังเป็นของปลอม**
ซึ่งกระทบความน่าเชื่อถือมากกว่ารายการอื่นที่เหลือทั้งหมดเพราะเป็นสิ่งที่ลูกค้าเจอวันแรกที่ใช้งาน —
**ปิดแล้ว** ดู `docs/tickets/16-promptpay-qr.md`

| # | ฟีเจอร์ที่ขาด | ทำไมสำคัญ | สถานะ |
|---|---|---|---|
| 1 | เปิด/ปิดกะ + กระทบยอดเงินสด (Shift & Cash Drawer Reconciliation) | ไม่มี table `shift`/`cash_session` เลย ร้านจริงต้องนับเงินตั้งต้น/ปิดกะเทียบยอดระบบ ไม่งั้นตรวจสอบเงินหายไม่ได้ | ✅ เสร็จแล้ว |
| 2 | คืนเงินหลังชำระเงินแล้ว (Refund) | มีแค่ "cancel" ก่อนเสิร์ฟ/ก่อนจ่าย ไม่มี flow คืนเงินหลังจ่ายสำเร็จ ไม่มี table `refunds` เลย | ✅ เสร็จแล้ว |
| 3 | พิมพ์ใบเสร็จจริง (Thermal/ESC-POS printer) | ปัจจุบันมีแค่ใบเสร็จบนจอ (ตั้งใจไม่ทำตาม `docs/DECISIONS.md` เพราะเป็น demo) แต่ร้านจริงต้องมี | ✅ เสร็จแล้ว (LAN/WiFi — Bluetooth/USB ยังไม่ทำ ดู #11) |
| 4 | Offline mode | เน็ตร้านอาหารหลุดบ่อย ตอนนี้ order พึ่ง backend ตลอด ไม่มี local queue + sync กลับ | ✅ เสร็จแล้ว (เฉพาะสั่งเพิ่มเข้าออเดอร์เดิม ดู #13) |
| 16 | **PromptPay QR / payment gateway จริง** | `qr` ใน `PAYMENT_METHODS` เคยเป็นแค่ label ให้ cashier กดยืนยันเอง เหมือน `card`/`transfer` ทุกอย่าง — ไม่มี generate QR ตามมาตรฐาน PromptPay คู่แข่งในตลาดไทยทุกเจ้ามีเป็นมาตรฐานขั้นต่ำ | ✅ เสร็จแล้ว (generate QR จริงตามมาตรฐาน EMV QR — ยังไม่มี payment gateway/callback ตรวจสอบอัตโนมัติตามที่ตั้งใจแยกขอบเขตไว้ ดู `docs/tickets/16-promptpay-qr.md`) |

(EMV QR) ให้ลูกค้าสแกนจ่ายได้จริง แม้จะยังไม่ต้องมี payment gateway เต็มรูป (ตรวจสอบสถานะจ่าย
อัตโนมัติ) ก็ตาม — เป็นก้าวแรกที่ทำได้เร็วและกระทบภาพลักษณ์มากที่สุด

**#17 Audit ระดับบัญชี/การเงิน** — ผู้ใช้ระบุตั้งแต่ต้นว่าต้องการ audit "ทั้ง financial และ
restaurant manager" ticket 13 (เสร็จแล้ว) ปิดฝั่งผู้จัดการร้าน ("ใครสั่ง/แก้ไขออเดอร์") แต่ตรวจโค้ด
จริงพบว่าฝั่งบัญชียังไม่ครบ: `menu.service.js` (แก้ราคาเมนู), `promotion.service.js` (สร้าง/แก้/ลบ
โปรโมชัน), `ingredient.service.js` (ปรับสต๊อก/ต้นทุนมือ) **ไม่มีการเรียก `auditLogService.log()`
เลยสักจุดเดียว** — ข้อมูลหลักที่กระทบรายได้/ต้นทุนโดยตรงจึงตรวจสอบย้อนหลังไม่ได้ ต่างจาก
order-level discount ที่ log ครบแล้ว นอกจากนี้ audit log เองก็ยังไม่มีทาง export ให้ฝ่ายบัญชี และ
ยังไม่มี date range picker บน UI (ของค้างจาก `docs/DECISIONS.md` #21) — รายละเอียดเต็มดู
`docs/tickets/14-financial-audit-trail.md`

## ทิศทางใหม่: ระบบนิเวศ PaynEat (2026-09-25) — `docs/DECISIONS.md` #66

เจ้าของโปรเจกต์เริ่ม [PaynEat ERP](https://github.com/SuruchBoss/PaynEat-ERP) (repo แยก, public) สำหรับเชนร้านอาหาร
ที่คุมห่วงโซ่อุปทานเอง (ซัพพลายเออร์ → โรงงานของตัวเอง → สาขา) ไม่ใช่ gap ของ POS ในตารางข้างบน แต่เปลี่ยนบทบาท
ของ POS ในโหมดเลือกได้: **เมื่อเชื่อมต่อ ERP**, ERP เป็นเจ้าของวัตถุดิบ สาขา (และต่อไปคือเมนู ราคา สูตร) และยอดคงเหลือ
ของสาขา ส่วน POS ส่งยอดขายเข้า ERP ผ่าน outbox — **เมื่อไม่เชื่อมต่อ ทุกอย่างเหมือนเดิม** ร้านเดี่ยวไม่เสียอะไร

| # | งาน | สถานะ |
|---|---|---|
| 24 | log/metric ตามสัญญา telemetry v1.1 ของระบบนิเวศ (ให้ SherWhyve สืบสวนได้) | ✅ เสร็จแล้ว (#68) |
| 25 | โหมดเชื่อมต่อ ERP: ลงทะเบียน ดึง master data ตามเวอร์ชัน หน้าจัดการอ่านอย่างเดียว | ⏳ รอสัญญา v1 ฝั่ง ERP |
| 26 | ส่งยอดขายเข้า ERP ผ่าน outbox ครั้งเดียวแน่นอน | ⏳ รอ 25 และ 27 |
| 27 | ดึงเมนู ราคา ตัวเลือก สูตรจาก ERP (สัญญา v1.1) และผูกเมนูเดิมตอนเชื่อมต่อครั้งแรก | ⏳ รอ 25 และ ERP #16 |
| 28 | เข้าโหมดเชื่อมต่อจากไฟล์ตั้งค่า และ tag `v1.0.0` ให้เดโมคำสั่งเดียวของ ERP | ⏳ รอ 25–27 |

**รุ่นของระบบ (`docs/DECISIONS.md` #67):** POS เป็น Community ทั้งหมด ไม่มีรุ่นเสียเงิน รายได้ของ POS มาจากบริการเท่านั้น
รุ่นเสียเงินของระบบนิเวศอยู่ที่ ERP ([ADR-0015](https://github.com/SuruchBoss/PaynEat-ERP/blob/main/docs/adr/0015-editions-community-and-enterprise.th.md))

ช่องว่างที่รู้ตัวและบันทึกไว้แล้ว (ไม่ใช่ลืม): ยังไม่มี feed ยอดคงเหลือจาก ERP มาขึ้นป้าย "หมด" (ใช้ปิดขายด้วยมือไปก่อน),
การคืนเงิน/void หลังชำระยังไม่ส่งเข้า ERP ใน v1, ราคาแยกสาขายังไม่มีใน POS (ticket 27 แสดงความขัดแย้งแทนการเลือกเงียบๆ)

## การสื่อสารจุดขาย: เมนูแก้ปัญหา (2026-09-26) — `docs/DECISIONS.md` #70

ช่องว่างไม่ได้อยู่ที่ฟีเจอร์ แต่อยู่ที่การเล่า: ของที่ปิดช่องว่างในเอกสารนี้ไปแล้วเกือบทั้งหมดถูกแสดงเป็นรายการฟีเจอร์

## ค้าปลีก (ร้านหนังสือ ซูเปอร์มาร์เก็ต) — `docs/DECISIONS.md` #71

## คู่มือติดตั้งสำหรับเจ้าของร้าน (2026-09-26) — `docs/DECISIONS.md` #72

ช่องว่างที่เจ้าของชี้: ปุ่ม "คู่มือติดตั้ง" บนหน้า Landing พาไปที่ README บน GitHub ซึ่งเขียนให้นักพัฒนาอ่าน ปิดแล้วด้วยหน้า
`install*.html` สามภาษา (4 ทางเลือกตามคนติดตั้ง ปุ่มคัดลอกคำสั่ง เช็คลิสต์ก่อนใช้จริง วิธีแก้ปัญหา)

ช่องว่างที่พบระหว่างทำและ**ยังเปิดอยู่**: ตัวติดตั้ง Windows บรรทัดเดียวและ `docker compose up` แบบค่าเริ่มต้น build แอปเว็บให้ยิง API ที่
`localhost:3000` มือถือ/แท็บเล็ตในร้านจึงต่อเข้ามาไม่ได้จนกว่าจะตั้ง `API_BASE_URL` เป็น IP ของเครื่องแล้ว build ใหม่ — ทางแก้ถาวรคือให้
แอปเว็บหาที่อยู่ API จากที่อยู่ของหน้าเอง (หรือให้ nginx ใน image เดียวกันส่งต่อ `/api` ไปที่ backend) เพื่อให้ "เปิดเครื่องไหนก็ได้ในร้าน"
ใช้ได้ทันทีโดยไม่ต้องตั้งค่า ยังไม่ได้ทำเพราะต้องแก้โค้ดแอปและ image ของตัวติดตั้ง ตอนนี้คู่มือบอกวิธีตั้ง `API_BASE_URL` ไว้แทน

## ร้านที่ใช้แอปภาษาเกาหลี/อังกฤษ (2026-09-26) — `docs/DECISIONS.md` #74
