# Ticket: สำรองข้อมูลอัตโนมัติ และกู้คืนได้เองโดยไม่ต้องมีนักพัฒนา

**Priority:** 🔴 Critical — ต้องเสร็จก่อนร้านจริงร้านแรกใช้งาน
**สถานะ (2026-09-29):** ⏳ ยังไม่ได้ทำ — **ทำต่อจาก T22 (#86) ทันที ก่อนรอบ 2 ของ QA** (`docs/DECISIONS.md` #90)
**Ref:** `docs/DECISIONS.md` #90, #79 (migration แบบมีเวอร์ชัน ไม่มี down migration "ถอยเวอร์ชันใช้ backup"), #55/#57 (เซิร์ฟเวอร์อยู่ในร้าน)
**Blocked by:** ไม่มี — ไม่แตะโค้ดเรื่องเงิน จึงไม่ต้องรอรอบ 1 แต่ให้ทำหลัง T22 เพื่อไม่ให้สองงานชนกันใน `server.js`

## ปัญหา
ข้อมูลทั้งร้าน ทั้งยอดขาย กะ ใบกำกับภาษี ลูกค้า และสต๊อก อยู่ในไฟล์ SQLite ไฟล์เดียว (`DATABASE_FILE`, ค่าเริ่มต้น `data/payneat.sqlite`)
บนเครื่องในร้าน ทั้งโปรเจกต์ยังไม่มีการสำรองข้อมูลเลย ถ้าฮาร์ดดิสก์เสีย เครื่องหาย หรืออัปเดตแล้วต้องถอยเวอร์ชัน (DECISIONS #79 ไม่มี down migration)
ร้านจะเสียข้อมูลทั้งหมด และเจ้าของร้านทั่วไปไม่รู้ว่าต้องคัดลอกไฟล์ไหน การคัดลอกไฟล์ตรงๆ ระหว่างเซิร์ฟเวอร์ทำงานก็ไม่ปลอดภัย เพราะฐานข้อมูลใช้ WAL
(`backend/src/db/index.js`) ไฟล์ที่ได้อาจไม่ครบ

## ขอบเขตงาน

### 1. สร้างไฟล์สำรอง
- ใช้ online backup API ของ SQLite (`db.backup()` ของ better-sqlite3) **ห้ามคัดลอกไฟล์ตรงๆ** เพราะไม่ปลอดภัยกับ WAL
- เขียนลงชื่อชั่วคราวก่อน ตรวจ `PRAGMA integrity_check` ของไฟล์ที่ได้ ผ่านแล้วค่อย rename เป็นชื่อจริง ไฟล์ที่ไม่ผ่านให้ลบทิ้งและนับเป็นความล้มเหลว
- ชื่อไฟล์บอกเวลาและเหตุผล เช่น `payneat-2026-09-29T2215+0700-shift-close.sqlite` (ใช้เวลาท้องถิ่นของร้านในชื่อ ให้เจ้าของร้านหาเจอ)
- ระหว่างสำรองต้องขายต่อได้ ไม่ล็อกการขาย

### 2. สำรองเมื่อไหร่
| จังหวะ | เหตุผล |
|---|---|
| **ปิดกะ** (หลังบันทึก Z-report สำเร็จ) | เป็น "สิ้นวัน" ตามธรรมชาติของร้าน ไม่ขึ้นกับว่าเปิดเครื่องไว้ตอนกลางคืนไหม |
| **ทุก 6 ชั่วโมงระหว่างเซิร์ฟเวอร์ทำงาน** ถ้ามีข้อมูลเปลี่ยนตั้งแต่ครั้งก่อน | ร้านที่ไม่ปิดกะหรือเปิดข้ามวันยังมีสำรอง |
| **ก่อนรัน migration ตอนเปิดเครื่อง** เมื่อมี migration ที่ยังไม่ได้รัน | ทางถอยเวอร์ชันตาม DECISIONS #79 ถ้าสำรองไม่สำเร็จ **ห้ามรัน migration** และหยุดเปิดเครื่องพร้อมข้อความที่บอกวิธีแก้ |
| **กดเอง** ปุ่ม "สำรองข้อมูลตอนนี้" (admin เท่านั้น) | ก่อนย้ายเครื่องหรือก่อนอัปเดต |

การสำรองที่ล้มเหลวต้องไม่ทำให้การปิดกะล้ม ปิดกะสำเร็จตามปกติ แล้วแสดงคำเตือนแทน

### 3. เก็บที่ไหน และเก็บนานแค่ไหน
- `BACKUP_DIR` (ค่าเริ่มต้น `data/backups` ข้าง `DATABASE_FILE`)
- `BACKUP_COPY_DIR` (ไม่บังคับ) คือที่เก็บชุดที่สอง เช่น USB drive หรือโฟลเดอร์บน NAS ในร้าน ถ้าตั้งไว้ให้คัดลอกไฟล์ที่ตรวจแล้วไปอีกที่ด้วย
  ที่เก็บชุดที่สองล้มเหลวแยกจากชุดแรก และแสดงสถานะแยกกัน
- **ไม่ส่งขึ้นคลาวด์ในรอบนี้** หน้านโยบายความเป็นส่วนตัวสัญญาไว้ว่าแอปไม่ส่งข้อมูลออกไปไหน ถ้าจะทำต้องตัดสินใจใหม่
- เก็บทุกไฟล์ใน 48 ชั่วโมงล่าสุด, ไฟล์ล่าสุดของแต่ละวันย้อนหลัง `BACKUP_KEEP_DAYS` วัน (ค่าเริ่มต้น 30) และไฟล์ก่อน migration 90 วัน
  ลบไฟล์เก่าหลังสำรองใหม่สำเร็จเท่านั้น ห้ามลบจนเหลือ 0 ไฟล์
- ถ้าพื้นที่ดิสก์เหลือน้อยกว่า 2 เท่าของขนาดฐานข้อมูล ให้เตือนก่อนเริ่มสำรอง

### 4. ให้เจ้าของร้านเห็นสถานะ
- หน้าตั้งค่า (admin) มีส่วน "สำรองข้อมูล" แสดงเวลาที่สำเร็จล่าสุด, ขนาดไฟล์, ที่เก็บทั้งสองที่พร้อมสถานะแยกกัน และจำนวนไฟล์ที่เก็บอยู่
  พร้อมปุ่มสำรองตอนนี้
- **แถบเตือนบนหน้าหลักของ admin และ manager** เมื่อไม่ได้สำรองสำเร็จเกิน 26 ชั่วโมง หรือครั้งล่าสุดล้มเหลว เจ้าของร้านต้องรู้โดยไม่ต้องเข้าไปดูเอง
- metric `payneat_backup_last_success_timestamp_seconds` และ `payneat_backup_failures_total` ใน `/metrics` สำหรับร้านที่ต่อ monitoring
- log ระดับ `ERROR` เมื่อล้มเหลว ห้ามใส่ข้อมูลในฐานข้อมูลลง log

### 5. กู้คืน
- คำสั่ง `npm run db:restore -- <ไฟล์>` (และเทียบเท่าใน Docker และตัวติดตั้ง Windows) ทำตามลำดับนี้
  1. ตรวจว่าเซิร์ฟเวอร์ไม่ได้ทำงานอยู่ ถ้ายังทำงาน ปฏิเสธพร้อมบอกวิธีหยุด
  2. ตรวจ `integrity_check` ของไฟล์ที่จะกู้
  3. ปฏิเสธไฟล์ที่มี migration ใหม่กว่าที่แอปเวอร์ชันนี้รู้จัก บอกให้อัปเดตแอปก่อน
  4. สำรองฐานข้อมูลปัจจุบันเป็น `pre-restore-*` ก่อนแทนที่เสมอ
  5. แทนที่ไฟล์ แล้วเขียน audit log `system.restore` ลงฐานข้อมูลที่กู้แล้ว ระบุชื่อไฟล์ต้นทาง
- **ไม่มีปุ่มกู้คืนบนหน้าจอในรอบนี้** และ**ไม่มี API ดาวน์โหลดไฟล์สำรอง** ไฟล์สำรองมีทั้งเบอร์โทรลูกค้าและ hash รหัสผ่าน ให้เข้าถึงได้เฉพาะคนที่เข้าเครื่องเซิร์ฟเวอร์ได้

### 6. ความปลอดภัยของไฟล์สำรอง
- บน Linux และ Docker ตั้งสิทธิ์ไฟล์เป็น 0600 และโฟลเดอร์เป็น 0700
- `BACKUP_DIR` ต้องไม่อยู่ในโฟลเดอร์ที่เว็บเสิร์ฟ ถ้าตั้งผิดให้ปฏิเสธตอนเปิดเครื่อง
- ยังไม่เข้ารหัสไฟล์ในรอบนี้ ให้ระบุไว้ในข้อเสียที่ยอมรับ

### 7. เอกสาร
- คู่มือติดตั้ง (`install*.html` ทั้ง 3 ภาษา): หัวข้อ "สำรองและกู้คืนข้อมูล" สำหรับเจ้าของร้าน ภาษาง่าย มีภาพ
  - แนะนำให้ตั้ง `BACKUP_COPY_DIR` ไปที่อีกดิสก์ เพราะสำรองไว้บนดิสก์เดียวกันไม่ช่วยตอนดิสก์เสีย
  - ขั้นตอนกู้คืนทีละขั้น ทั้งบน Windows และ Docker
  - Docker: ให้ `BACKUP_COPY_DIR` เป็น bind mount ออกนอก volume `payneat-data`
- `backend/.env.example`: เพิ่มค่าใหม่ทุกตัวพร้อมคำอธิบาย
- `SECURITY.md`: ไฟล์สำรองมีข้อมูลส่วนบุคคลและ hash รหัสผ่าน ต้องเก็บในที่ที่คนนอกเข้าไม่ถึง
- README ไทย/อังกฤษ/เกาหลี (ทัวร์ 5 นาทีเพิ่มขั้นตอนดูสถานะและกดสำรอง), `docs/DECISIONS.md` #90, `docs/FEATURE-GAP-ANALYSIS.md` ตาม `CLAUDE.md`

## Acceptance Criteria
- [ ] ปิดกะ → มีไฟล์สำรองใหม่ที่ผ่าน `integrity_check` และเปิดอ่านยอดของกะนั้นได้
- [ ] ระหว่างสำรองฐานข้อมูลขนาดใหญ่ (เทสต์ด้วยข้อมูลหลายหมื่นออเดอร์) ยังรับชำระเงินได้ และไฟล์สำรองไม่มีรายการครึ่งๆ กลางๆ
- [ ] มี migration ใหม่ → สำรองก่อนรัน, ถ้าสำรองล้มเหลว (เช่น `BACKUP_DIR` เขียนไม่ได้) เซิร์ฟเวอร์ไม่เปิดและไม่มี migration ถูกรัน
- [ ] `BACKUP_COPY_DIR` ชี้ไปที่ที่เขียนไม่ได้ → ชุดแรกยังสำเร็จ หน้าตั้งค่าแสดงว่าชุดที่สองล้มเหลว
- [ ] ไม่ได้สำรองสำเร็จเกิน 26 ชั่วโมง → admin และ manager เห็นแถบเตือน ส่วน cashier และ waiter ไม่เห็น
- [ ] การเก็บย้อนหลังลบไฟล์เก่าตามกติกา และไม่ลบจนเหลือ 0 ไฟล์แม้ตั้ง `BACKUP_KEEP_DAYS=0`
- [ ] `db:restore` ขณะเซิร์ฟเวอร์ทำงาน → ปฏิเสธ; ไฟล์เสีย → ปฏิเสธ; ไฟล์จากเวอร์ชันใหม่กว่า → ปฏิเสธ; ไฟล์ปกติ → กู้ได้ มี `pre-restore-*` และ audit `system.restore`
- [ ] ไม่มี endpoint ใดส่งไฟล์สำรองออกไป และ cashier/waiter/kitchen เรียกปุ่มสำรองตอนนี้ได้ 403
- [ ] README ไทย/อังกฤษ/เกาหลี, คู่มือติดตั้ง 3 ภาษา, `SECURITY.md`, `docs/DECISIONS.md` #90 และ `docs/FEATURE-GAP-ANALYSIS.md` อัปเดตตาม `CLAUDE.md`

## เทสต์
- backend: สำรองตอนปิดกะ, ตามรอบเวลา (จำลองนาฬิกา), ก่อน migration (รวมกรณีล้มเหลวแล้วไม่ migrate), กฎการเก็บย้อนหลัง, สิทธิ์ของปุ่ม,
  สำรองพร้อมกับการเขียนต่อเนื่อง, คำสั่งกู้คืนทั้ง 4 กรณี

- E2E: ปิดกะแล้วมีไฟล์สำรอง จากนั้นกู้คืนลงฐานข้อมูลใหม่แล้วยอดของกะตรงกัน
