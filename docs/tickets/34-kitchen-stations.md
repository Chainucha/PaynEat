**Priority:** 🟠 High — ร้านที่มีบาร์หรือครัวเย็นแยกจากครัวร้อนใช้จอครัวเดียวร่วมกันไม่ไหว
**สถานะ (2026-10-04):** ✅ เสร็จแล้ว — รายละเอียดการตัดสินใจอยู่ใน `docs/DECISIONS.md` #94

**Blocked by:** ไม่มี

## ปัญหา
คิวครัวมีคิวเดียว `GET /orders/kitchen/queue` คืนรายการที่ยังไม่เสิร์ฟของทุกออเดอร์ และจอครัวแสดงทั้งหมด
เรียงเป็นสามคอลัมน์ตามสถานะ ร้านที่แยกครัวร้อน ครัวเย็น และบาร์ จึงให้แต่ละสถานีมีจอของตัวเองไม่ได้ —
แท็บเล็ตที่บาร์ขึ้นผัดกะเพรา จอหน้าเตาขึ้นน้ำปั่น พนักงานต้องกวาดตาข้ามตั๋วที่ไม่ใช่งานของตัวเองทุกครั้ง

## ขอบเขตงาน

### 1. ตารางอ้างอิง `kitchen_stations`
- migration `0006_kitchen_stations` สร้างตาราง (`code` ไม่ซ้ำ, ชื่อไทย/อังกฤษ/เกาหลี, ไอคอน, ลำดับ,
  เปิดใช้งาน, ธงค่าเริ่มต้น) พร้อมสามสถานีตั้งต้น: ครัวร้อน (ค่าเริ่มต้น), ครัวเย็น, บาร์
- ไม่มี `branch_id` — เป็นข้อมูลระดับเครือร้านเหมือน `categories` เพราะหมวดหมู่ซึ่งถือค่าเริ่มต้นของสถานี
  ก็เป็นข้อมูลระดับเครือร้านอยู่แล้ว
- `is_default` เป็นคอลัมน์ ไม่ใช่คีย์ใน `settings` และมี partial unique index บังคับว่ามีได้ไม่เกินหนึ่งสถานี
- โมดูล `modules/kitchen-stations/` ครบ 6 ไฟล์ตามแบบ `modules/categories/` — อ่านได้ทุกบทบาทที่ล็อกอิน
  (จอครัวต้องอ่านไปทำชิป) เขียนได้เฉพาะ admin/manager

### 2. กฎการตัดสินสถานีของจาน
- `menu_items.station_id` → `categories.station_id` → สถานีค่าเริ่มต้น
- ทั้งสองคอลัมน์เป็น nullable: `null` ที่เมนูหมายถึง "ตามหมวดหมู่" และ `null` ที่หมวดหมู่หมายถึง
  "ใช้ค่าเริ่มต้น" จึงต้องเขียน `NULL` ลงฐานข้อมูลได้จริง (ไม่ใช้ `COALESCE(?, col)`)
- ตัดสินที่ `buildItemRow` ใน `order.service.js` ที่เดียว ซึ่งเป็นทางผ่านของทุกวิธีที่เพิ่มรายการ:
  พนักงานเปิดบิล, สั่งเพิ่มเข้าออเดอร์ที่ส่งครัวไปแล้ว และลูกค้าสแกน QR สั่งเอง

### 3. ประทับสถานีลงตั๋ว
- `order_items` เก็บทั้ง `station_id` และ `station_name_snapshot` (คู่เดียวกับ `menu_item_id` +
  `name_snapshot`) ย้ายเมนูไปสถานีอื่นหรือเปลี่ยนชื่อสถานีภายหลังจึงไม่กระทบตั๋วที่ครัวกำลังทำอยู่
- ไม่ใส่ `ON DELETE SET NULL`: NO ACTION ทำให้ฐานข้อมูลปฏิเสธการลบสถานีที่เคยมีตั๋วอ้างถึง ประวัติบน
  บิลเก่าจึงหายเงียบ ๆ ไม่ได้ (service ปิดทางด้วย 409 ก่อนถึงฐานข้อมูลอยู่แล้ว)
- migration ประทับสถานีค่าเริ่มต้นให้ตั๋วที่ค้างอยู่บนจอครัวตอนอัปเกรด (`pending`/`cooking`/`ready` ของ
  ออเดอร์ `in_kitchen`/`served`) รายการของบิลที่ปิดแล้วคงเป็น `NULL` เพราะตอนนั้นยังไม่มีสถานีอยู่จริง

### 4. จอครัว
- แถวชิป `ทุกสถานี | ครัวร้อน | ครัวเย็น | บาร์` อยู่ใต้หัวจอ เป็นแถวของตัวเอง ไม่ยัดเข้า `Wrap` ของหัวจอ
- สถานีที่เลือกถูกจำ **ต่อเครื่อง** (`StorageKeys.kitchenStation` เก็บรหัสสถานี) ไม่ถูกล้างตอน logout
  เพราะแท็บเล็ตของบาร์ติดอยู่ที่บาร์ ไม่ว่าใครจะล็อกอินอยู่
- กรองในเครื่องจากคิวที่โหลดมาแล้ว (ใช้ได้แม้ตอน socket หลุด) ทุกอย่างที่จอแสดง — คอลัมน์, ตัวนับคิว,
  ตัวนับจานช้า — อ่านผ่าน `visibleQueue` ที่เดียว
- ตั๋วแสดงป้ายชื่อสถานีเฉพาะตอนดู "ทุกสถานี"
- ร้านที่มีสถานีเดียว (หรือดึงรายการสถานีไม่สำเร็จ) ไม่เห็นแถบชิปเลย และเห็นตั๋วทั้งหมดตามปกติ

### 5. ฟอร์มเมนูและหมวดหมู่
- ฟอร์มเมนูมีดรอปดาวน์สถานี ตัวเลือกแรกคือ "ตามหมวดหมู่ (ชื่อสถานีที่ตกลง)" ซึ่งเป็นค่าปกติของเมนูส่วนใหญ่
- กล่องแก้หมวดหมู่มีดรอปดาวน์สถานีตั้งต้นของหมวด
- ชีตจัดการสถานีอยู่ในหน้าจัดการเมนู (แบบเดียวกับชีตหมวดหมู่) ไม่เพิ่มหน้าใหม่: เพิ่ม/แก้/ลบ ตั้งค่าเริ่มต้น
  และป้าย "ค่าเริ่มต้น" `code` แก้ไม่ได้หลังสร้าง

### 6. ความถูกต้องของคิวครัว (แก้ของเดิมที่พลาดไว้)
- `GET /orders/kitchen/queue` ไม่เคยมี zod ตรวจ query — `?status=junk` ลงไปถึง SQL ได้ ตอนนี้ตรวจแล้ว
- คิวครัวกรองตามสาขาของผู้ใช้ เหมือนที่รายการออเดอร์ทำอยู่ (admin โหมด "ทุกสาขา" ยังเห็นทุกสาขา)

### 7. โหมดสาธิต
มิเรอร์กฎทั้งหมดในโหมดสาธิต (`docs/DECISIONS.md` #8): สามสถานีตั้งต้น, สถานีของหมวดหมู่, กฎการตัดสิน,
การประทับลงตั๋ว, CRUD พร้อม 409 ทั้งสี่กรณี และการย้ายค่าเริ่มต้น

## ขอบเขตที่ตั้งใจไม่ทำ
- **ห้องเรียลไทม์ต่อสถานี** — `KITCHEN_TICKET` ส่งทั้งออเดอร์ซึ่งมีรายการของหลายสถานีในใบเดียว ไม่มี payload
  ต่อสถานีให้ route และห้องถูกเข้าตามบทบาทจาก JWT ซึ่งไม่มีสถานีอยู่ในนั้น ใช้ห้อง `room:kitchen` เดิมแล้วให้
  ฝั่งแอปกรอง
- **ผูกสถานีกับบัญชีพนักงาน** — สถานีเป็นเรื่องของเครื่อง ไม่ใช่ของคน บัญชีครัวบัญชีเดียวใช้ได้ทุกจอ
  *(ข้อนี้ถูกเพิ่มเข้ามาภายหลังใน ticket 35 — ดู `docs/DECISIONS.md` #95 ซึ่งแก้ข้อ "ไม่ทำ" ข้อนี้ของ #94)*
- **สถานีต่อสาขา** — เครือร้านใช้ชุดสถานีร่วมกัน สาขาที่ไม่มีบาร์จะเห็นชิปบาร์ที่ว่าง
- **เครื่องพิมพ์ตั๋วต่อสถานี** — ยังไม่มีการพิมพ์ตั๋วครัวเลย (`docs/DECISIONS.md` #11 พิมพ์แค่ใบเสร็จ)
- **รายงานแยกตามสถานี** — ยังไม่มี
- **`categories.name_ko`** — ตาราง `categories` ยังไม่มีคอลัมน์ชื่อเกาหลี (แอปส่งมาแล้ว backend ตัดทิ้ง)
  ticket นี้ไม่แก้ แต่ `kitchen_stations` มี `name_ko` ตั้งแต่ต้นเพราะเป็นตารางใหม่

## Acceptance Criteria
- [x] `GET /kitchen-stations` คืนครัวร้อน/ครัวเย็น/บาร์ โดยครัวร้อนเป็นค่าเริ่มต้นเพียงสถานีเดียว
- [x] เมนูที่กำหนดสถานีเอง → ตั๋วไปสถานีนั้น; ไม่กำหนดแต่หมวดหมู่กำหนด → ไปสถานีของหมวดหมู่;
      ไม่กำหนดทั้งคู่ → ไปสถานีค่าเริ่มต้น
- [x] ย้ายเมนูไปสถานีอื่นหลังตั๋วเข้าครัวแล้ว → ตั๋วใบนั้นยังอยู่สถานีเดิม ใบใหม่ไปสถานีใหม่
- [x] เปลี่ยนชื่อสถานี → ชื่อบนตั๋วที่ค้างอยู่ไม่เปลี่ยน
- [x] `PATCH /menu-items/:id` ด้วย `stationId: null` → เมนูกลับไปใช้สถานีตามหมวดหมู่ (เขียน NULL ได้จริง)
      และไม่ส่ง `stationId` มาเลย → ค่าเดิมไม่ถูกแตะ
- [x] `stationId` ที่ไม่มีจริง → 400 ทั้งที่เมนูและหมวดหมู่
- [x] `GET /orders/kitchen/queue?station=bar` คืนเฉพาะตั๋วของบาร์; `?station=nope` → 404;
      `?status=junk` และ `?status=` → 422
- [x] รายการที่สั่งเพิ่มเข้าออเดอร์ที่ส่งครัวไปแล้ว และรายการที่ลูกค้าสั่งเองผ่าน QR มีสถานีประทับครบ
- [x] เมนูที่ถูกลบภายหลัง (`menu_item_id` กลายเป็น NULL) ตั๋วยังรู้สถานีของตัวเอง เพราะเก็บเป็น snapshot
- [x] waiter/cashier/kitchen เรียก `GET /kitchen-stations` ได้ 200 แต่ POST/PATCH/DELETE ได้ 403
      และไม่ล็อกอินได้ 401
- [x] ปลดธงค่าเริ่มต้น ปิดใช้งานสถานีค่าเริ่มต้น หรือลบสถานีค่าเริ่มต้น → 409 ทั้งสามกรณี
- [x] ลบสถานีที่ยังมีเมนู/หมวดหมู่ผูกอยู่ หรือที่เคยอยู่บนตั๋ว → 409 พร้อมเหตุผล (ไม่ใช่ SQLITE_CONSTRAINT)
- [x] `itemCount` ของสถานีนับจานที่ตกลงสถานีนั้นจริงตามกฎการตัดสิน ไม่ใช่แค่จานที่ผูกตรง ๆ
- [x] migration อัปเกรดฐานข้อมูลที่มีตั๋วค้างอยู่ได้โดยตั๋วไม่หายจากทุกชิป และข้อมูลเดิมไม่หาย
- [x] จอครัว: แตะชิป → คอลัมน์และตัวนับจานช้ากรองตามสถานีนั้น, ค่าที่เลือกอยู่รอดการรีเฟรช,
      สถานีที่จำไว้แต่ถูกลบไปแล้วเด้งกลับเป็น "ทุกสถานี", สถานีเดียวไม่ขึ้นแถบชิป และกว้าง 360px ไม่ล้น
- [x] ข้อความ error ใหม่ทุกข้อความมีคำแปลอังกฤษ/เกาหลีใน `src/i18n/errorMessages.js`
- [x] README ไทย/อังกฤษ/เกาหลี, `docs/DECISIONS.md` #94, `docs/FEATURE-GAP-ANALYSIS.md` และ
      `backend/docs/openapi.yaml` อัปเดตตาม `CLAUDE.md`

## เทสต์
- backend: CRUD + สิทธิ์ + 409 ทุกกรณีของสถานี, กฎการตัดสินและการประทับลงตั๋ว (รวมย้ายเมนู/เปลี่ยนชื่อ

  ของแถบชิปรวมกรณี 360px
