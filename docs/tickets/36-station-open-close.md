# Ticket: ปิด/เปิดสถานีครัวรายสาขา — จานของสถานีที่ปิดสั่งไม่ได้

**Priority:** 🟠 High — บาร์ปิดสามทุ่มแต่ลูกค้ายังสั่งน้ำปั่นผ่าน QR ได้ ตั๋วเข้าจอที่ไม่มีคนเฝ้า
**สถานะ (2026-10-08):** ✅ เสร็จแล้ว — รายละเอียดการตัดสินใจอยู่ใน `docs/DECISIONS.md` #102 (คำศัพท์อยู่ใน `CONTEXT.md`)
**Ref:** `docs/DECISIONS.md` #97 (สถานีครัว), #98 (ผูกพนักงานกับสถานี — ค่าตั้งต้น ไม่ใช่ล็อก), #36 (การแยกสาขา),
#79 (migration แก้ไม่ได้หลัง merge), #8 (โหมดสาธิต), #99 (เพดานออเดอร์ QR — ทางเดียวกับที่ปฏิเสธ submit)
**Blocked by:** ไม่มี · ทำคู่กับ ticket 37 ได้ (ไม่แตะไฟล์เดียวกันมาก)

## ปัญหา
สถานีครัวมีแค่ "เปิดใช้งาน/ปิดใช้งาน" (`kitchen_stations.is_active`) ซึ่งเป็นค่าตั้งระดับเครือร้าน ใช้บอกว่า
"เครือนี้ไม่มีเตาย่าง" ไม่ใช่ "บาร์สาขานี้ปิดแล้วคืนนี้" ร้านที่บาร์ปิดก่อนครัวจึงต้องไล่ปิดขายเมนูทีละจาน
(`is_available`) แล้วไล่เปิดคืนทีละจานตอนเช้า ซึ่งยังไปทับเมนูที่ระบบสต๊อกปิดไว้เองด้วย

## คำศัพท์ (ดู `CONTEXT.md`)
- **สถานีปิด (closed station)** ≠ **สถานีที่ปิดใช้งาน (inactive station)** — ปิด = เรื่องหน้างานรายสาขา ชั่วคราว
  เปิดคืนแตะเดียว; ปิดใช้งาน = ค่าตั้งของเครือร้าน
- **จานที่สั่งได้ (orderable dish)** = จานที่ `is_available` **และ** สถานีของจานเปิดอยู่ที่สาขานั้น

## ขอบเขตงาน

### 1. สถานะปิดต่อ (สาขา, สถานี)
- migration `0008_station_closures`: ตาราง `station_closures (branch_id, station_id, closed_at, closed_by)`
  PK `(branch_id, station_id)` — **มีแถว = ปิด**, เปิดคืน = ลบแถว ไม่มีแถว = เปิด (สาขาใหม่/สถานีใหม่เปิดเสมอ)
- `ON DELETE CASCADE` ทั้งสาขาและสถานี — แถวนี้เป็นสถานะปัจจุบัน ไม่ใช่ประวัติ ประวัติอยู่ใน audit log
- สถานีที่ปิดใช้งาน (`is_active = 0`) ไม่แสดงในรายการสถานะ แถวปิดที่ค้างอยู่ไม่มีผลอะไร
- **ไม่แตะ `menu_items.is_available` เลย** — "สั่งได้" คำนวณตอนอ่าน การปิดสถานีจึงไม่ล้างการปิดขายที่พนักงาน
  หรือระบบสต๊อกตั้งไว้ และเปิดคืนแล้วกลับสู่สถานะเดิมพอดี

### 2. API
- `GET /kitchen-stations/status` — สถานะของสาขาปัจจุบัน (`req.branchId`): ทุกสถานีที่เปิดใช้งาน พร้อม
  `isClosed`, `closedAt`, `closedByName`, และ `pendingCount` (รายการ pending/cooking ของสถานีนั้นในสาขานี้)
- `POST /kitchen-stations/:id/close` และ `POST /kitchen-stations/:id/open` — idempotent (ปิดซ้ำ/เปิดซ้ำได้ 200)
- สิทธิ์: `GET /status` อ่านได้ทุกบทบาทที่ล็อกอิน (แบนเนอร์บนหน้าสั่งอาหารของพนักงานเสิร์ฟต้องใช้)
  ส่วนปิด/เปิดได้เฉพาะ kitchen, manager, admin — kitchen ปิดได้ **ทุกสถานี** ในสาขาของตัวเอง ไม่จำกัดเฉพาะ
  สถานีที่ผูก (#98) waiter/cashier ปิด/เปิด → 403
- admin โหมด "ทุกสาขา" (ไม่มี `branchId`) → 400 ต้องเลือกสาขาก่อน
- ทุกการปิด/เปิดลง audit log (ใคร, สาขา, สถานี, จำนวนรายการที่ค้างตอนปิด)
- ข้อความ error ใหม่มีคำแปลใน `src/i18n/errorMessages.js` และอัปเดต `backend/docs/openapi.yaml`

### 3. ผลต่อการสั่ง
- `buildItemRow` (ทางผ่านเดียวของพนักงานเปิดบิล, สั่งเพิ่ม, ลูกค้า QR) ตัดสินสถานีอยู่แล้ว — เพิ่มตรวจว่าสถานี
  ที่ตัดสินได้ปิดอยู่ที่สาขาของออเดอร์ไหม ถ้าปิด → **409 ทั้ง submit** พร้อมชื่อจานและสถานี
  ("บาร์ปิดอยู่: ชาไทยเย็น") เหมือนที่เมนูปิดขายถูกปฏิเสธทุกวันนี้ ตะกร้าฝั่งแอปไม่ถูกล้าง
- `sendToKitchen` ของออเดอร์ที่บันทึกไว้แต่ยังไม่ส่งครัว (`status = open`) ตรวจซ้ำ — สถานีอาจปิดไประหว่างที่บิลรอ
  ถ้ามีรายการของสถานีที่ปิด → 409 ไม่ส่งอะไรเลย (ออเดอร์ที่อยู่ในครัวแล้วไม่ต้องตรวจ รายการสั่งเพิ่มถูกตรวจตอนเพิ่ม)
- **ไม่มีการถอยไปสถานีอื่น** — สถานีค่าเริ่มต้นปิด = จานที่ตกลงค่าเริ่มต้นสั่งไม่ได้ทั้งหมด
- รายการที่อยู่ในคิวแล้วไม่ถูกแตะ — ครัวทำต่อจนเสร็จ ยกเลิก/แก้ได้ตามกฎเดิม

### 4. เมนู
- `GET /menu-items` (พนักงาน): DTO เพิ่ม `stationClosed` (bool) และชื่อสถานีที่ตัดสินได้ แอปแสดงจานเป็นสีเทา
  พร้อมป้าย "บาร์ปิด" — พนักงานต้องรู้เหตุผลเพื่อบอกลูกค้า
- `GET /public/tables/:qrToken/menu` (ลูกค้า): **ซ่อน** จานของสถานีที่ปิด เหมือนที่ซ่อนจานปิดขายอยู่แล้ว
  ลูกค้าไม่เห็นข้อความว่าสถานีไหนปิด

### 5. เรียลไทม์
- event ใหม่ `station:status` `{ branchId, stationId, isClosed, closedAt, closedByName }` ส่งเข้าห้อง kitchen,
  service, management — ห้องแยกตามบทบาท ไม่แยกสาขา ฝั่งแอปทิ้ง event ของสาขาอื่น
- หน้าสั่งอาหารของพนักงานและจอครัวรีเฟรชสถานะทันที หน้า QR ของลูกค้าไม่ฟัง (ได้ค่าใหม่ตอนโหลด/submit;
  ช่องว่างระหว่างนั้นถูกปิดด้วย 409 ในข้อ 3)

### 6. แอป
- **ชีต "สถานะสถานี"** (widget เดียว ใช้สองที่): รายการสถานีของสาขานี้ แต่ละแถวมีสวิตช์เปิด/ปิด, เวลาและคนที่ปิด
  ปิดสถานีที่ยังมีรายการค้าง → ยืนยันพร้อมข้อความ "ยังมี N รายการค้าง — ครัวทำต่อจนเสร็จ" (เตือน ไม่บล็อก)
  - เปิดจากปุ่มบนหัวจอครัว (ชิปสถานีใช้กรองอย่างเดียว ไม่ใช่สวิตช์ — กันแตะผิด)
  - เปิดจากหน้าสั่งอาหารของพนักงาน เฉพาะ manager/admin
  - **ไม่อยู่ในหน้าจัดการเมนู** — หน้านั้นเป็นค่าตั้งระดับเครือร้าน
- **แบนเนอร์เฉพาะพนักงาน** บนหน้าสั่งอาหารและจอครัว: "บาร์ปิดตั้งแต่ เมื่อวาน 21:03 โดย สมชาย" — กันลืมเปิดคืน
  (ไม่มีการเปิดคืนอัตโนมัติ) ไม่แสดงฝั่งลูกค้า
- การ์ดเมนูในหน้าสั่งอาหาร: จานของสถานีที่ปิดเป็นสีเทา แตะไม่ได้ มีป้ายชื่อสถานี
- 409 จากข้อ 3 แสดงข้อความชัดเจน ตะกร้าคงอยู่
- ข้อความใหม่ทุกข้อมีไทย/อังกฤษ/เกาหลี

### 7. โหมดสาธิต
มิเรอร์ครบ (#8): ตารางปิดในหน่วยความจำ, สถานะ + pendingCount, ปิด/เปิดซ้ำได้, 409 ตอนสั่ง, ซ่อนในเมนู QR,
`stationClosed` ในเมนูพนักงาน, สิทธิ์ตามบทบาท

## ขอบเขตที่ตั้งใจไม่ทำ
- **เวลาเปิด–ปิดตามตาราง/เปิดคืนอัตโนมัติ** (ตอนเปิดกะ, เที่ยงคืน) — แยกเป็นฟีเจอร์ "เวลาทำการของสถานี" ภายหลัง
- **ถอยไปสถานีอื่นเมื่อสถานีปิด** — ส่งตั๋วไปสถานีที่ทำจานนั้นไม่ได้แย่กว่า "สั่งไม่ได้"
- **บอกลูกค้าว่าสถานีไหนปิด** — ฝั่ง QR แค่ซ่อนจาน
- **แก้ `is_active` ให้เป็นรายสาขา** — คนละแนวคิดกัน (ดูคำศัพท์)
